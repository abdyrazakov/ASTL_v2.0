# ASTL — пополосный анализ дорожного движения (этап 1)

Этап 1 проекта Adaptive Smart Traffic Light: локальное приложение, которое по видео с
перекрёстка строит пополосную аналитику трафика — очереди, ожидание, пересечения,
состав транспорта. Включает визуальный редактор разметки полос и панель анализа.

Этапы 2–4 (симулятор, координация перекрёстков, макет на Raspberry Pi) в этот документ
не входят. Формат профиля и экспортируемых данных спроектирован так, чтобы симулятор на
этапе 2 мог генерировать данные той же структуры.

## 1. Состав системы

- **Backend**: Python 3.11, FastAPI, OpenCV, Ultralytics YOLO (детекция) + ByteTrack
  (трекинг, через `model.track(..., tracker="bytetrack.yaml")`). Анализ видео выполняется
  в фоновом потоке (worker), API остаётся отзывчивым во время обработки.
- **Frontend**: React 19 + TypeScript + Vite, Konva/react-konva (редактор разметки),
  Recharts (графики), Tailwind CSS 4.
- Работает **на CPU**. Если доступна CUDA — используется автоматически
  (`torch.cuda.is_available()`), иначе CPU. На этой машине CUDA не обнаружена, все
  измерения ниже — для CPU.

## 2. Установка

Требуются: Python 3.11+, Node.js 20+, ffmpeg (для перекодирования итогового видео в
H.264), git.

```bash
cd smart_traffic

# backend
python3.11 -m venv backend/.venv
backend/.venv/bin/pip install -r backend/requirements.txt

# frontend
cd frontend
npm install
cd ..
```

### Загрузка модели

Веса `yolo11n.pt` (~5 МБ) скачиваются **автоматически при первом запуске** анализа —
библиотека Ultralytics сама скачивает файл в рабочую директорию backend. Повторные
запуски используют уже скачанный файл без обращения к сети. Для демонстрации без
интернета — заранее запустите один анализ при наличии сети, либо положите файл
`yolo11n.pt` в `smart_traffic/backend/` вручную.

После первой установки зависимостей и загрузки весов приложение работает полностью
локально, без внешних API и CDN (см. раздел «Известные ограничения» про шрифты).

## 3. Запуск

Два процесса, в двух терминалах (dev-режим):

```bash
# терминал 1 — backend
cd smart_traffic/backend
.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8420

# терминал 2 — frontend
cd smart_traffic/frontend
npm run dev
```

Открыть `http://127.0.0.1:5173`.

**Продакшен-сборка одной командой** (frontend собирается статикой, backend отдаёт её
сам — тогда достаточно одного процесса и порта 8420):

```bash
cd smart_traffic/frontend && npm run build && cd ..
backend/.venv/bin/python -m uvicorn app.main:app --host 0.0.0.0 --port 8420 --app-dir backend
```

## 4. Работа с редактором («Настройка камеры»)

1. Выберите видео из списка или загрузите новое (`+ Загрузить видео`).
2. Ползунком под кадром выберите удобный момент — первый кадр может быть закрыт
   машинами.
3. Выберите существующий профиль или нажмите «Создать новый».
4. «+ Добавить полосу» запускает управляемый сценарий из трёх шагов:
   - **область наблюдения** — кликами задайте вершины полигона полосы, `Enter` —
     завершить (минимум 3 точки), `Esc` — отменить всю полосу;
   - **зона очереди** — полигон внутри полосы (по умолчанию предлагается уменьшенная
     копия области наблюдения, её можно подвинуть/изменить до `Enter`);
   - **линия подсчёта** — два клика задают концы линии, третий — точку направления
     (стрелка рисуется от линии к этой точке; засчитываются только пересечения со
     стороны, противоположной этой точке, в сторону точки — см. раздел 7).
5. Инструмент «выделение»: клик по полосе — выбрать, перетаскивание точек — править
   форму, двойной клик по вершине — удалить (если вершин ≥ 4), двойной клик по границе
   полигона — вставить вершину.
6. `Ctrl+Z` / `Ctrl+Shift+Z` — отмена/повтор (история до 100 шагов).
7. Панель справа: имя, цвет, направление подсчёта (по стрелке / против / в обе стороны),
   переопределение опорной точки конкретной полосы.
8. «Сохранить профиль» — валидация на сервере (уникальность ID/имён, отсутствие
   самопересечений, зона очереди строго внутри полосы, ненулевая длина линии) и запись в
   `backend/data/profiles/`. «Дублировать» — копия текущего профиля.
9. При выборе видео с другим соотношением сторон, чем у загруженного профиля,
   приложение **не** применяет его молча — показывает предупреждение и просит выбрать
   другой профиль или создать новый.

Координаты полигонов хранятся нормализованными (0..1) относительно исходного
разрешения видео — масштаб окна редактора не сдвигает разметку.

## 5. Запуск анализа («Анализ движения»)

1. Выберите видео и профиль вверху (переносятся из редактора автоматически).
2. «▶ Запустить анализ». Одновременно может выполняться только одно задание — повторный
   запуск до завершения предыдущего вернёт ошибку 409, а не второй конфликтующий worker.
3. Пока модель загружается в память — показывается состояние «Загрузка модели».
   Во время работы видно обработанное видео (прямой просмотр), боковые карточки полос,
   историю очереди и пересечений выбранной полосы, журнал событий.
4. «⏸ Пауза» — обработка кадров останавливается, время видео замораживается, ожидание
   машин не растёт. «▶ Продолжить» возобновляет с того же кадра. «■ Остановить»
   завершает задание досрочно — экспорт формируется по уже обработанной части.
5. После завершения (или остановки) видео превращается из прямого просмотра в обычный
   `<video>` с перемоткой; графики синхронизированы со временем видео, а не с моментом
   показа кадра на экране.
6. Переключатели слоёв (рамки/ID/траектории/полосы/зоны очереди/линии) применяются к
   новым кадрам по мере их отрисовки на сервере — это не ретроактивный фильтр поверх уже
   записанного видео (см. раздел 8).
7. ⛶ — полноэкранный режим демонстрации.

## 6. Экспорт

Каждый запуск анализа создаёт `output/<run_id>/`:

| Файл | Содержимое |
|---|---|
| `annotated_video.mp4` | обработанное видео с отрисованными слоями (H.264) |
| `traffic_metrics.csv` | временной ряд показателей по полосам (по одной строке на полосу на тик) |
| `traffic_state.json` | последний согласованный снимок состояния (атомарная запись) |
| `traffic_history.jsonl` | история снимков, один JSON-объект на строку |
| `profile.json` | копия профиля, использованного в запуске |
| `run_metadata.json` | ID запуска/профиля/видео, модель, устройство, итоговый статус |

Скачать можно прямо по ссылке `/output/<run_id>/<файл>` или кнопкой «⬇ Экспорт» на
панели анализа.

## 7. Определения показателей

Все интервалы — по **времени видео** (`timestamp_sec`), не по времени обработки. Пауза
не продвигает это время.

- **vehicles** — число отслеживаемых машин, чей трек сейчас (или в пределах
  `track_lost_grace_sec`, по умолчанию 1 с; для стоящих машин —
  `stationary_track_retention_sec`, 4 с) назначен этой полосе и находится в её
  полигоне наблюдения.
- **queued** — число машин в состоянии `waiting` (см. ниже) с опорной точкой внутри
  зоны очереди полосы.
- **avg_wait_sec / max_wait_sec** — среднее/максимум **накопленного наблюдаемого**
  времени ожидания среди машин, сейчас находящихся в состоянии `waiting` на этой полосе
  (`video_time − момент начала остановки`). Если машина уже стояла в момент начала
  ролика, её прошлое ожидание неизвестно и не учитывается — считается только
  наблюдаемый период.
- **flow_count_window / flow_window_available_sec** — число пересечений линии за
  последние `flow_window_target_sec` (по умолчанию 60) секунд видео и реальная
  длительность доступного окна (пока не накопилась полная минута — показывается
  меньшее число, не выдаётся за полное окно).
- **total_crossings** — сумма всех засчитанных пересечений за запуск.
- **vehicle_types** — состав по классам среди **уникальных треков, когда-либо
  назначенных этой полосе** за время запуска (не мгновенный снимок — иначе выборка из
  1–3 машин была бы слишком шумной для столбца состава).
- **queue_truncated_by_frame** — зона очереди касается края кадра → в интерфейсе
  показывается как «очередь в зоне наблюдения», а не как полная длина реальной очереди.

### Состояние очереди: moving → waiting → moving

Скорость считается нормированной: смещение опорной точки за окно сглаживания
(`speed_window_sec`, по умолчанию 0.8 **секунды видео**, не кадров), делённое на высоту
рамки машины и на время — это частично компенсирует перспективу (чем ближе к камере, тем
крупнее рамка). Окно намеренно задано в секундах, а не в кадрах: при высоком fps источника
окно в несколько кадров покрывает только доли секунды, и обычное дрожание рамки детектора
(несколько пикселей даже у неподвижной машины) превращается в ложную скорость, намного
превышающую пороги — машина никогда не "затихает" достаточно долго, чтобы попасть в
очередь. Это реальный баг ранней версии, найденный при проверке на настоящем видео (см.
`VERIFICATION.md`) и исправленный переходом на оконное сглаживание по времени.

- `moving → waiting`: усреднённая опорная точка внутри зоны очереди **и** не дальше
  `stop_max_drift_bbox_h` (0.2 высоты рамки) от места остановки **непрерывно** не менее
  `stop_duration_threshold_sec` (по умолчанию 2 с). Момент начала ожидания — начало этого
  непрерывного интервала, а не момент регистрации перехода. Критерий — смещение, а не
  мгновенная скорость: рамка слабой (мелкой, дальней, частично закрытой) детекции у
  неподвижной машины медленно плывёт, и её «скорость» держалась выше прежнего порога
  `stop_enter_speed=0.08` (см. `VERIFICATION.md`, раздел 7.7).
- `waiting → moving`: точка вышла из зоны очереди **или** скорость выше `stop_exit_speed`
  (1.0 высоты рамки/с) — непрерывно не менее `queue_exit_duration_sec` (1 с). Подтягивание
  за передней машиной (около высоты рамки за пару секунд) — это всё ещё ожидание в той же
  очереди и его не сбрасывает. Сохранённое в старых профилях значение 0.2 (прежний
  умолчательный, с которым подтягивание обнуляло ожидание) при загрузке заменяется на 1.0.
- Стоящая машина, которую детектор временно потерял, удерживается
  `stationary_track_retention_sec` (4 с) и всё это время считается в очереди. Если трекер
  завёл ей новый ID (рядом с прежним местом или с рамкой, перекрывающей прежнюю), её
  ожидание переходит к новому ID, а старый удаляется — машина не считается дважды.
- Трекер: ByteTrack держит потерянный трек `tracker_buffer_sec` (3 с, в кадрах источника) и
  получает от модели детекции от `tracker_low_conf` (0.1) — ими продлеваются уже
  существующие треки; новые треки по-прежнему создаются только от `conf_threshold`.

### Пересечение линии

Линия задаётся двумя точками `p1 → p2` и точкой направления. Положительная сторона
определяется знаком векторного произведения `(p2−p1) × (point−p1)` в точке направления.
Пересечение засчитывается, если отрезок движения машины (предыдущая → текущая опорная
точка) геометрически пересекает именно отрезок линии (не бесконечную прямую), в заданном
направлении. Каждый трек засчитывается на каждой линии не более одного раза за запуск —
это и есть защита от повторного счёта при дрожании рамки у линии.

Опорная точка по умолчанию — «низ по центру рамки», но не буквально на нижнем крае: точка
приподнята на 2/5 расстояния от центра рамки до нижней стороны (= 0.3 высоты рамки выше
нижнего края). Нижний край рамки детектора часто проходит по тени/отражению, а не по
фактической точке контакта колёс с дорогой — приподнятая точка точнее на этом ракурсе
камеры (подобрано визуально, как и предупреждал исходный ТЗ). При необходимости
переопределяется в профиле (глобально или по полосе).

Скорость в км/ч и длина очереди в метрах **не вычисляются** — координаты не
откалиброваны к реальным единицам измерения.

## 8. Важные ограничения дизайна (прочитать перед демонстрацией)

- Переключатели слоёв на панели анализа меняют то, что **сервер рисует поверх новых
  кадров** — отрисовка выполняется на бэкенде (единая логика для прямого просмотра и
  экспортируемого видео), поэтому переключение не ретроактивно перекрашивает уже
  показанные/записанные кадры. Для живого MJPEG-просмотра это полноценная переключаемая
  функция, для уже завершённого видео переключатели значения не имеют (видео уже
  готово).
- Во время выполнения задания видео показывается как «живой» поток кадров (MJPEG) —
  это не перематываемый плеер. Перемотка и точная синхронизация графиков с конкретным
  кадром доступны **после** завершения/остановки задания, когда воспроизводится
  финальный `annotated_video.mp4`.
- `cv2.VideoWriter` пишет видео в кодеке MPEG-4 Part 2, который не проигрывается в
  браузерах — поэтому по завершении запуска видео автоматически перекодируется в H.264
  через `ffmpeg`. Если `ffmpeg` недоступен в системе, в `run_metadata.json` попадёт
  сообщение об ошибке и видео останется в исходном кодеке (не воспроизведётся в
  браузере, но файл не теряется).
- Интерфейс не использует внешние шрифтовые CDN: применяется системный шрифтовой стек
  (Inter/Segoe UI/Roboto и аналоги по платформе), чтобы приложение гарантированно
  работало полностью офлайн после установки. Это сознательный выбор в пользу надёжности
  офлайн-работы, а не недосмотр.
- MVP держит не более одного активного задания одновременно (явное требование этапа 1).
  Повторный запуск до завершения текущего возвращает ошибку, а не второй worker.
