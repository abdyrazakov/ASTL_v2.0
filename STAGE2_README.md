# ASTL — этап 2: управление одним перекрёстком в симуляторе

Собственная дискретно-временная симуляция одного перекрёстка: генератор трафика →
движение и очереди по полосам → пополосная аналитика (те же поля, что в этапе 1) →
контроллер фаз (фиксированный цикл **или** адаптивный, переключается на лету) →
автомат сигналов с жёстким инвариантом безопасности → экспорт и интерфейс.

Что проверено и какие числа реально измерены — в [`VERIFICATION_STAGE2.md`](VERIFICATION_STAGE2.md).
Исходное ТЗ — [`docs/STAGE2_SPEC.md`](docs/STAGE2_SPEC.md).

## 1. Установка и запуск

Установка — та же, что в этапе 1 (см. `README.md`, раздел 2). Симулятор не требует
ничего сверх зависимостей этапа 1 и не использует модель YOLO, камеру или видео.

```bash
cd ASTL_v2.0
python3.11 -m venv backend/.venv
backend/.venv/bin/pip install -r backend/requirements.txt   # для torch CPU: --extra-index-url https://download.pytorch.org/whl/cpu
cd frontend && npm install && cd ..
```

**Одна команда запуска** (frontend собран статикой, backend отдаёт его сам):

```bash
cd frontend && npm run build && cd .. && \
backend/.venv/bin/python -m uvicorn app.main:app --host 0.0.0.0 --port 8420 --app-dir backend
```

Открыть `http://127.0.0.1:8420/intersection` (редактор) или `/simulation`.
Dev-режим (два терминала: uvicorn на 8420 + `npm run dev` на 5173) работает так же,
как в этапе 1.

Тесты: `backend/.venv/bin/python -m pytest backend/tests/` (634 теста, ~3.5 мин;
этапы 1 и 2 вместе).

## 2. Редактор перекрёстка («Настройка перекрёстка»)

1. «Шаблон» → «+ Создать из шаблона» (под панелью — описание выбранного шаблона).
   Профиль сразу сохраняется на сервере. Шаблонов 11, все разные:

   | Шаблон | Подходы × полосы | Фазы | Что показывает |
   |---|---|---|---|
   | 4-подходный простой | 4 × 1 | 2 | самая простая схема, без левых |
   | 4-подходный с выделенными левыми | 4 × 2 | 4 | защищённые левые повороты |
   | T-образный | 3 (1/2/1) | 3 | примыкание, отдельная левая |
   | 4-подходный, 3 полосы | 4 × 3 | 4 | классический городской перекрёсток |
   | 4-подходный, 3 полосы, расщеплённые фазы | 4 × 3 | 4 | каждый подход едет отдельно всеми манёврами |
   | 4-подходный, 3 полосы: утро / вечер / ночь | 4 × 3 | 4 | сценарий на час: два пика, всплеск, ночной спад |
   | Магистраль × второстепенная | 3/3 + 1/1 | 4 | главная с автобусами, всплеск «конец уроков» |
   | T-образный, главная 3 полосы | 3 (3/3/2) | 3 | группа в нескольких фазах (перекрытия), 25% грузовиков |
   | Две односторонние улицы | 2 × 3 | 2 | только два подхода, выезды без въездов |
   | Асимметричный, короткие подходы | 3/2/1/2 | 4 | участки 60–150 м, очередь выходит за участок («+N») |
   | Бульвар со сдвоенными левыми | 4/4 + 2/2 | 4 | две левоповоротные полосы, подходы 250 м |

   Матрицы конфликтов первых трёх шаблонов написаны вручную. Для остальных они
   подготовлены по явной таблице правил правостороннего движения
   (`backend/app/simulation/templates_extra.py`, `movement_conflict`), и тест
   подтверждает, что на первых трёх эта таблица даёт ровно ручные матрицы. В
   профиле матрица хранится явно и редактируется вручную. Для профилей
   пользователя система конфликты не выводит.
2. Слева — схема сверху; клик по полосе выбирает её. Цвет стоп-линии — сигнальная
   группа манёвра; на вкладках «Группы»/«Фазы» подсвечиваются полосы выбранной
   группы/фазы.
3. Вкладки справа:
   - **Полосы** — подходы (С/В/Ю/З — сторона, с которой едут машины), полосы подхода
     от осевой к обочине, разрешённые манёвры (↰ ↑ ↱), длина (м), интенсивность (маш/ч).
   - **Сигнальные группы** — группа = один сигнал для набора манёвров. Манёвр,
     уже занятый другой группой, недоступен (манёвр — ровно в одной группе).
   - **Конфликты** — матрица чекбоксов; отметка ставится сразу в обе клетки.
   - **Фазы** — набор групп, горящих одновременно; конфликтующие с уже выбранными
     группы недоступны. Порядок (↑/↓) — цикл фиксированного режима. Зелёный
     фиксированного цикла, переопределение min/max для фазы. Допустимые переходы:
     «из любой в любую» или явная матрица (переходы цикла обязательны).
   - **Тайминги** — min/max зелёный, жёлтый, all-red, all-red при старте, gap-out,
     защита от голодания, расстояние детектора, вес ожидания w.
   - **Трафик** — seed, минимальная дистанция, интенсивность по полосам, состав
     (легковые/автобусы/грузовики/мотоциклы — классы этапа 1), сценарий (множители
     интенсивности на интервалах времени; кнопка «+ всплеск на выбранной полосе»).
4. Валидация идёт на сервере при каждом изменении и при сохранении (те же правила).
   Ошибки блокируют сохранение и запуск, предупреждения — нет.
5. «Сохранить профиль», «Дублировать», «Удалить». Хранение:
   `backend/data/intersections/<profile_id>.json`.

### Правила валидации (жёсткие)

- матрица конфликтов симметрична, группа не конфликтует сама с собой;
- фаза не содержит конфликтующих групп; каждая группа входит хотя бы в одну фазу;
- каждый манёвр полосы с ненулевой интенсивностью привязан ровно к одной группе,
  и эту группу обслуживает хотя бы одна фаза — иначе машины копились бы вечно
  (для полосы с нулевой интенсивностью — только предупреждение);
- фаз минимум две; порядок фаз содержит каждую фазу ровно раз; переходы цикла
  разрешены; из каждой фазы есть хотя бы один переход;
- `min_green ≤ fixed_green ≤ max_green` для каждой фазы; `yellow ≥ 3 с`; все
  длительности > 0;
- `max_red_wait_sec ≥ min_green + 2·(yellow + all_red)` — иначе защита от голодания
  физически не может уложиться в срок (см. раздел 5.3);
- полосы в сценарии существуют; ID уникальны; один подход на сторону.

Все длительности квантуются шагом модели 0.1 с.

## 3. Симуляция («Симуляция»)

Верхняя панель: перекрёсток, seed, длительность (10 мин … 2 ч или ∞), переключатель
**фиксированный / адаптивный** (до запуска — начальный режим, во время прогона —
переключение на лету), скорость ×1/×5/×50 (меняется на лету), запуск / пауза /
продолжить / остановить, «⬇ Экспорт» (все файлы прогона). Строка состояния: статус,
модельное время и прогресс (или «бесконечный режим»), фактическая скорость, состояние
автомата сигналов, текущая фаза и оставшееся время (в адаптивном режиме помечено
«≈ … (расчётное)» — может измениться).

- **Схема**: полосы, машины (цвет — класс, красная обводка — стоит в очереди),
  стоп-линии окрашены в текущий сигнал своей группы. «+N» у начала полосы — машины,
  не поместившиеся на моделируемый участок. Значок «✓ конфликтов сигналов нет» —
  счётчики предохранителя автомата.
- **Справа**: итог по перекрёстку, карточки полос этапа 1 (тот же компонент) с блоком
  новых показателей, журнал событий этапа 1.
- **Снизу**: история очереди и пересечений (графики этапа 1; клик по полосе — график
  этой полосы), **длительность зелёного по фазам** (каждая точка — один зелёный; в
  фиксированном режиме точки на горизонтальных линиях, в адаптивном — следуют за
  спросом; моменты переключения режима отмечены), **сравнение средней задержки
  фиксированный vs адаптивный**.

Сравнение строится только из реально выполненных и сохранённых прогонов с тем же
содержимым профиля (хэш), тем же seed и той же длительностью, завершённых полностью и
без переключения режима. Если такой пары нет, панель так и пишет: «для сравнения
запустите оба режима на одном сценарии». Кнопка «⇄ Прогнать оба режима (быстро)»
выполняет оба прогона без отрисовки, «как можно быстрее» (≈1–3 с на час модельного
времени), и сохраняет их в `output/` как обычные прогоны.

Одновременно активен один прогон (повторный запуск → 409), как задания в этапе 1.
Пауза останавливает **модельное время**, а не только отрисовку: ожидание и задержка на
паузе не растут.

## 4. Показатели

Все времена — модельные секунды. Пауза их не продвигает.

### Поля этапа 1 (имена и смысл сохранены; здесь это точные значения, не оценки)

| Поле | Определение в симуляции |
|---|---|
| `vehicles` | машин на участке полосы, ещё не проехавших стоп-линию |
| `queued` | из них в состоянии `waiting` (стоят в очереди, см. ниже) |
| `avg_wait_sec` / `max_wait_sec` / `wait_sample_size` | по машинам, которые **сейчас** в очереди (встали и ещё не проехали стоп-линию, включая не поместившихся на участок): время от момента, когда машина встала в очередь, до текущего момента. Это **полное** ожидание — без оговорки этапа 1 «только наблюдаемый период»: начало жизни машины в модели известно |
| `flow_count_window` / `flow_window_available_sec` / `flow_window_target_sec` | проезды стоп-линии за последние 60 с (и реально доступное окно в начале прогона) |
| `total_crossings` | проезды стоп-линии за прогон |
| `vehicle_types` | состав по классам среди всех машин, прибывших на полосу |
| `queue_truncated_by_frame` | **всегда `false`** — кадра в симуляции нет. Аналог — новое поле `queue_spillback` |

### Новые показатели этапа 2 — агрегаты по ВЫБЫВШИМ машинам

«Выбывшая» машина — проехавшая стоп-линию этой полосы. `departed_count` — размер
выборки.

- **`avg_delay_sec`** — средняя задержка на машину: `(момент проезда стоп-линии −
  момент прибытия) − длина участка / свободная скорость`, где свободная скорость —
  `min(предел скорости класса, лимит полосы)`. Включает торможение, стояние, разгон и
  ожидание въезда, если очередь вышла за начало участка.
- **`stops_per_vehicle`** — среднее число остановок (переходов `moving → waiting`) на
  машину; ожидание въезда за пределами участка — одна остановка.
- **`throughput_per_hour`** (по полосе) — пропускная способность за скользящее окно:
  `flow_count_window · 3600 / flow_window_available_sec`, маш/ч. В итоге по прогону
  (`totals`, `summary.json`) — `выбывшие за прогон · 3600 / модельное время`.
- Также: `avg_departed_wait_sec`, `max_departed_wait_sec` (полное ожидание выбывших:
  от остановки до проезда линии), `max_delay_sec`, `entry_backlog` (сколько машин не
  поместилось на участок), `arrival_rate_vph_now` (интенсивность с учётом сценария),
  `signals` (сигнал по каждому манёвру полосы).

Итог по перекрёстку (`totals`): средние по всем выбывшим машинам перекрёстка
(взвешены по машинам, а не по полосам), `vehicles_in_system` — ещё не выбывшие.

### Состояние очереди: `moving → waiting → moving`

- `moving → waiting`: скорость < 0.5 м/с **и** машина в очереди у стоп-линии: до линии
  ≤ 1 м, **или** впереди идущая (ещё не проехавшая линию) машина сама в `waiting` и
  зазор до неё ≤ `min_gap_m` + 1 м. Порога длительности (как 2 с в этапе 1) нет:
  данные модели точные, дрожания детектора нет.
- `waiting → moving`: скорость ≥ 1.0 м/с (гистерезис против дребезга, когда очередь
  подползает).
- Эпизод очереди начинается с **первого** перехода в `waiting` и заканчивается только
  проездом стоп-линии: подползание не обнуляет накопленное ожидание (как в этапе 1).

## 5. Сигнальная логика

### 5.1 Объекты

Сигнальная группа (набор манёвров полос), матрица конфликтов (задаётся вручную, не
выводится из геометрии), фаза (набор неконфликтующих групп), циклический порядок фаз
и допустимые переходы.

### 5.2 Автомат состояний (`backend/app/simulation/signals.py`)

```
STARTUP_ALL_RED ──(startup_all_red_sec)──▶ GREEN(p)
GREEN(p) ──(≥ min_green; решение контроллера или ровно max_green)──▶ YELLOW(p)
YELLOW(p) ──(ровно yellow_sec)──▶ ALL_RED
ALL_RED ──(ровно all_red_clearance_sec)──▶ GREEN(q)
любое ──(нарушение безопасности / ошибка контроллера)──▶ FAULT
FAULT ──(1 тик, всё красное)──▶ STARTUP_ALL_RED (перезапуск)
```

Допустимые переходы заданы таблицей `ALLOWED_TRANSITIONS`; любой другой — ошибка → FAULT.
Отклонения от схемы ТЗ:

- FAULT длится один тик и ведёт в STARTUP_ALL_RED, который сам держит всё красное не
  меньше `startup_all_red_sec` — это и есть «ALL_RED (restart)».
- Группа, входящая и в текущую, и в следующую фазу, всё равно проходит жёлтый и
  all-red (без «перекрытий»): проще и заведомо безопасно.
- `max_green` — жёсткий предел в обоих режимах, даже если других заявок нет: тогда
  инвариант `min_green ≤ зелёный ≤ max_green` выполняется всегда.
- Решение принимается в начале шага по спросу на этот же момент; сигнал, выставленный
  на шаге, действует весь шаг. Все длительности — в целых тиках (0.1 с), поэтому
  тайминги соблюдаются точно.

**Инвариант безопасности** — две группы из матрицы конфликтов никогда не показывают
разрешающий (зелёный/жёлтый) сигнал одновременно — обеспечен двумя независимыми слоями:
1. структурно: зелёный включается только из полностью красного состояния и только
   для групп одной фазы, а валидация не пропускает фазы с конфликтами;
2. предохранитель `_apply_signals`: **каждая** смена сигналов проверяется по матрице;
   конфликтующий набор не выставляется ни на один тик, автомат уходит в FAULT (всё
   красное), растёт счётчик `blocked_violations`. Это проверено тестом на профиле,
   собранном в обход валидации.

Ещё одна страховка на уровне машин: на красном стоп-линия как препятствие, а при
попытке её пересечь машина принудительно останавливается (`red_clamps`, в норме 0).

### 5.3 Контроллеры (`backend/app/simulation/controllers.py`)

Контроллер только предлагает «закончить зелёный, следующая фаза q». Min/max зелёный,
жёлтый, all-red и допустимость перехода обеспечивает автомат.

**Фиксированный (baseline).** Фаза горит ровно `fixed_green_sec`, затем следующая по
циклу. Спрос не учитывается. Защиты от голодания нет — это контрольная группа.

**Адаптивный — «простое правило по наибольшему спросу с защитой от голодания».** Это
эвристика, а не оптимизация: не max-pressure, не RL и не какой-либо опубликованный
алгоритм.

Спрос (по фактическому состоянию модели):

```
D(g) = Σ по машинам v в очереди к группе g (встали и ещё не проехали линию, вкл. ожидающих въезда) (1 + w · wait_v)
D(p) = Σ по группам g фазы p  D(g)
```

Единица — одна машина в очереди. Слагаемое `w · wait_v` (w = `wait_weight_per_sec`,
по умолчанию 0.1 1/с) добавляет машине одну «условную машину» за каждые 1/w = 10 с
ожидания. Без него одинокая машина на редкой полосе проигрывала бы любой очереди из
двух машин вплоть до срабатывания защиты от голодания. Сумма равна
`queued_g + w · Σ wait`, то есть взвешенной сумме числа ждущих и их суммарного
ожидания.

Окончание зелёного активной фазы p (проверяется только после `min_green`, по порядку):

1. **Защита от голодания**: у группы вне p есть машина, у которой `ожидание + жёлтый +
   all-red ≥ max_red_wait_sec` → закончить; следующая — фаза, обслуживающая эту группу
   (напрямую, если переход разрешён, иначе первый шаг кратчайшего пути разрешённых
   переходов).
2. **Gap-out**: с последнего «срабатывания» прошло ≥ `gap_out_sec` **и** у другой фазы
   `D > 0` → закончить. Срабатывание — машина фазы p проехала виртуальный детектор
   (`detector_distance_m` до стоп-линии) или саму стоп-линию. Если активной фазе
   пропускать некого, срабатываний нет, и фаза уступает сразу после `min_green` («не
   держать зелёный впустую»).
3. **Очистка очереди**: у фазы p не осталось машин в очереди (все вставшие проехали
   стоп-линию), а спрос другой фазы `D ≥ queue_clear_min_demand` (по умолчанию 2.0,
   примерно две ждущие машины; пусто — правило выключено) → закончить, даже если на p
   ещё подъезжают машины со свободной скоростью. Без этого правила на 2–3-полосных
   фазах gap-out почти не срабатывал: машины с разных полос проезжают детектор чаще,
   чем раз в `gap_out_sec`, и зелёный тянулся до `max_green`. Правило добавлено по
   результатам эксперимента (VERIFICATION_STAGE2.md, раздел 6).
4. Иначе зелёный продлевается. Если у других фаз спроса нет, зелёный «отдыхает» на p,
   но не дольше `max_green` (обрывает автомат).

Выбор следующей фазы: сначала голодающая (если её отложить ещё на одну чужую фазу,
она опоздает: `ожидание ≥ max_red_wait − (жёлтый + all-red) − (max min_green + жёлтый
+ all-red)`); иначе допустимая фаза с наибольшим `D(p)`; при равенстве — ближайшая по
циклу; если спроса нет нигде — следующая по циклу. После старта — фаза с наибольшим
спросом.

**Гарантия защиты от голодания**: при одном голодающем направлении и
`max_red_wait_sec ≥ min_green + 2·(жёлтый + all-red)` (проверяется валидацией) его фаза
получает зелёный не позже `max_red_wait_sec` с момента, когда машина встала в очередь.
Худший случай: машина встаёт ровно тогда, когда чужая фаза уходит в жёлтый, а
следующей уже выбрана другая чужая фаза. Гарантия касается **момента зелёного для
фазы**, а не проезда каждой машины: в длинной очереди хвост может не успеть за один
зелёный, и тогда полное ожидание конкретной машины больше `max_red_wait_sec`. При
одновременном голодании нескольких направлений они обслуживаются по старшинству
ожидания, и каждое следующее может опоздать на `min_green + жёлтый + all-red`.

Смена режима на лету не прерывает текущий интервал: новые правила действуют со
следующего решения. Прогон с переключением помечается (`controller_mode_switches`) и
не участвует в честном сравнении режимов.

### 5.4 Трафик и движение (`backend/app/simulation/engine.py`)

- Прибытия — независимый пуассоновский поток на каждой полосе (`arrival_rate_vph`);
  сценарий умножает интенсивность на интервалах (неоднородный поток через
  прореживание). Класс — по долям состава, манёвр — равновероятно из разрешённых
  манёвров полосы.
- У каждой полосы свой генератор `random.Random(f"{seed}|{lane_id}")`, используемый
  только для прибытий. Поэтому при одном seed в обоих режимах приходят одни и те же
  машины (проверено тестом), и сравнение режимов честное.
- Кинематика упрощённая (не IDM): `v' = min(v + a·dt, v_max, √(2·b·d), d/dt)`, где d —
  расстояние до препятствия (задний бампер впереди идущей минус `min_gap_m`, либо
  стоп-линия на красном). На жёлтом машина останавливается, если успевает
  (`d ≥ v²/2b`), иначе проезжает. Классы: легковой 4.5 м, a = 2.5, b = 3.5; автобус
  12 м, 1.2/2.5, ≤ 12 м/с; грузовик 10 м, 1.0/2.5, ≤ 12.5 м/с; мотоцикл 2.2 м, 3.5/4.0.
  Внутри перекрёстка машины не взаимодействуют (конфликты исключает сигнальная логика)
  и удаляются, проехав условный путь манёвра.
- Измеренный поток насыщения одной полосы (только легковые, `min_gap_m = 2`):
  ≈ 2170 маш/ч (интервал ~1.66 с). Это выше типичных ~1900 маш/ч; калибруется
  параметром `min_gap_m`.

## 6. Формат данных и экспорт

Каждый прогон — `output/<run_id>/`:

| Файл | Содержимое |
|---|---|
| `traffic_state.json` | последний снимок (атомарная запись) — **схема снимка этапа 1 + новые поля** |
| `traffic_history.jsonl` | снимок каждую секунду модельного времени |
| `traffic_metrics.csv` | первые 18 колонок — **ровно колонки этапа 1** в том же порядке, затем `avg_delay_sec, stops_per_vehicle, throughput_per_hour, departed_count, entry_backlog, controller_mode, signal_state, active_phase, phase_remaining_sec` |
| `phase_log.jsonl` | каждый завершённый зелёный: фаза, начало, конец, длительность, причина (`fixed`/`gap_out`/`max_out`/`starvation`), режим, следующая фаза |
| `signal_log.jsonl` | каждый переход автомата с полным набором сигналов групп — запись прогона для проверки конфликтов |
| `events.jsonl` | смены режима и скорости, пауза/продолжение |
| `summary.json` | итог прогона: totals, по полосам, по фазам, safety, отпечаток траекторий |
| `profile.json` | профиль перекрёстка (схема `intersection` 2.0 — **не** схема полигонов этапа 1) |
| `run_metadata.json` | `schema_version: "2.0"`, `kind: "simulation"`, `seed`, `controller_mode` (начальный) и `controller_mode_final`, переключения, `duration_sec`, `dt_sec`, `profile_hash`, параметры генератора трафика (интенсивности, состав, `min_gap_m`, сценарий, способ генерации), тайминги, итоговый статус, `safety` |

### Совместимость с этапом 1 и версии схем

- **Снимок** (`traffic_state.json` / строки `traffic_history.jsonl`):
  `schema_version: "1.1"` — обратно совместимое надмножество версии 1.0 этапа 1: все
  поля этапа 1 на месте и с тем же смыслом, существующие не переименованы, только
  добавлены. Верхний уровень: добавлены `source: "simulation"`, `controller_mode`,
  `signal_state`, `active_phase`, `next_phase`, `phase_remaining_sec`,
  `phase_remaining_is_estimate`, `signals` (сигнал каждой группы), `totals`, `safety`,
  `seed`. Поэтому карточки полос, графики очереди/пересечений и журнал событий этапа 1
  используются на экране симуляции без изменений (в `LaneCards` добавлен только
  необязательный слот `extra` для новых показателей).
- **Расхождения** (неизбежные, задокументированы и в коде):
  `queue_truncated_by_frame` всегда `false` (кадра нет; аналог — `queue_spillback`);
  `avg_wait_sec`/`max_wait_sec` — полное ожидание, а не наблюдаемое; `vehicles` —
  машины на моделируемом участке, а не в полигоне наблюдения.
- **Профиль перекрёстка** — новая схема (`kind: "intersection"`, `schema_version:
  "2.0"`), отдельная от профиля разметки видео этапа 1 (`schema_version: "1.0"`): это
  разные сущности.
- **run_metadata** — `schema_version: "2.0"`: несовместимо с 1.0 (нет полей видео и
  модели, есть seed/режим/генератор), поэтому версия увеличена и добавлено
  `kind: "simulation"`.

## 7. Известные ограничения (честно)

- **Это учебная демонстрация логики, а не дорожно-инженерный контроллер**: не
  NEMA/ГОСТ, не сертифицируется и не готов к внедрению.
- **Кинематика упрощённая**: постоянное ускорение/торможение, без car-following модели
  (IDM и подобных), без взаимодействия машин внутри перекрёстка, без уступания дороги
  (поэтому левые повороты в шаблонах либо отсутствуют, либо защищённые), без
  пешеходов. Реалистичность физики движения не заявляется. Числа внутренне согласованы
  и воспроизводимы, но абсолютные значения задержки не откалиброваны по реальным
  наблюдениям.
- **Матрица конфликтов задаётся вручную**: система проверяет её симметричность и
  согласованность с фазами, но **не** соответствие реальной геометрии перекрёстка — это
  ответственность того, кто настраивает профиль.
- **Адаптивный алгоритм — простое эвристическое правило**, не оптимизация (не
  max-pressure, не RL). Он не обязан выигрывать по каждому показателю. В измерениях
  (VERIFICATION_STAGE2.md, раздел 6) он снижает среднюю задержку на всех 11 шаблонах.
  Но на сценарии «утро/вечер/ночь» остановок на машину у него больше (1.44 → 2.16),
  там же на одном seed из пяти задержка хуже. Редкие левые повороты иногда ждут
  дольше, чем в фиксированном цикле (8 случаев из 20 на шаблоне с выделенными левыми).
- Манёвр в многоманёвровой полосе выбирается равновероятно (доли поворотов не
  настраиваются); машина, чей манёвр на красном, блокирует полосу (как в реальности,
  без «кармана»).
- Пропускная способность в недонасыщенном режиме равна спросу: проезжают все пришедшие
  машины, поэтому разница режимов по throughput видна только при перегрузке.
- **Один перекрёсток**: координации нескольких перекрёстков (этап 3) и вывода на
  реальные светофоры/GPIO (этап 4) нет. Структура данных для будущей интеграции
  заложена, но не реализована: снимок содержит сигнал каждой группы (`signals`) и
  состояние автомата, а профиль — явные группы/фазы/тайминги. Этого достаточно, чтобы
  будущий модуль координации или драйвер GPIO читал состояние, однако сами они не
  реализованы.
- Живая схема обновляется опросом (~7 раз/с), поэтому на ×50 машины визуально
  «прыгают» — модель от этого не зависит.
- Состояние прогонов в памяти не переживает перезапуск сервера. Результаты на диске
  (`output/`) сохраняются и доступны для сравнения (`/api/simulations/runs`).
